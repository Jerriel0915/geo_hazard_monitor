# 告警中心系统模块 — 开发规划与实施指南

**日期：** 2026-06-08
**版本：** v1.0
**作者：** 系统架构设计

---

## 一、背景与目标

### 1.1 现状

系统在设备接入闭环（注册→认证→上报→解析→落库→查询）和设备管理闭环方面已基本完整。但在业务价值闭环（采集→告警→通知→处置）方面*
*完全缺失**：

- `alarm_criteria` / `alarm_record` / `alarm_notification` / `alarm_dispatch_rule` 四张表已在数据库中定义，但**零 Java 代码
  **
- `MonitorIngestConsumerService.processRecord()` 在 IoTDB 写入成功后直接返回，**无告警评估钩子**
- `DashboardStatService.getHealthScore()` 的告警响应率硬编码为 100.0，标注为 `placeholder`
- 国标协议解析 (`GbMonitorPayloadParser`) 抛出 `ServiceException("暂未实现")`

### 1.2 目标

根据 `docs/告警中心.md` 业务需求，建设完整的告警中心模块，包括：

1. **待办告警** — 告警处理工作台（列表/筛选/处置/批量操作）
2. **历史告警** — 告警档案与审计（归档/查询/导出）
3. **告警判据** — 基础阈值规则引擎（多级告警/复合判据/抗抖动）
4. **综合告警** — 高阶策略引擎（实时/周期/脚本/多参数融合）

### 1.3 关键约束

- 与现有 IoT 模块架构保持一致（Maven 多模块、Service 接口跨模块调用、Spring Events 解耦）
- 复用现有基础设施（Redis Stream、IoTDB 时序查询、SSE 推送、NotifyChannelDispatcher）
- 告警通知渠道 SYSTEM 复用现有 SSE 推送，SMS/EMAIL 预留接口但本期不落地

## 二、架构总览


## 三、数据库设计

### 3.1 表结构变更策略

现有四张表 `alarm_criteria` / `alarm_record` / `alarm_notification` / `alarm_dispatch_rule` 需要**重大重构**
以匹配业务需求。由于告警模块尚无生产数据，采用**DROP + 重建**策略，在 `db/upgrade/` 目录放置增量迁移脚本。

### 3.2 告警判据表 (`alarm_criteria`) — 重构

```sql
-- db/upgrade/V2.1__alarm_module_schema.sql

DROP TABLE IF EXISTS `alarm_criteria`;
CREATE TABLE `alarm_criteria` (
    `id`                bigint       NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    `name`              varchar(200) NOT NULL COMMENT '判据名称',
    `monitor_type_id`   bigint       DEFAULT NULL COMMENT '监测类型ID（FK→monitor_type）',
    `monitor_type_name` varchar(200) DEFAULT NULL COMMENT '监测类型名称（冗余，查询提速）',
    `monitor_content_id` bigint      DEFAULT NULL COMMENT '监测内容ID（FK→monitor_content，精确到指标）',
    `monitor_content_code` varchar(100) DEFAULT NULL COMMENT '监测内容编码',
    `hazard_point_id`   bigint       DEFAULT NULL COMMENT '隐患点ID（NULL=监测类型下全局适用）',
    -- 核心判据规则 — JSON 存储多条件组合
    -- 格式: [{"indicator":"value","operator":"GT","threshold":10.5,"unit":"mm"}]
    `conditions_json`   json         DEFAULT NULL COMMENT '判据条件列表（JSON数组）',
    `logic_operator`    varchar(10)  DEFAULT 'AND' COMMENT '多条件逻辑: AND / OR',
    -- 分级告警表达式（可选，为空时仅用 conditions_json + 阈值分级）
    `blue_expression`   varchar(500) DEFAULT NULL COMMENT '蓝色预警表达式或阈值描述',
    `blue_description`  varchar(500) DEFAULT NULL COMMENT '蓝色预警描述',
    `yellow_expression` varchar(500) DEFAULT NULL COMMENT '黄色预警表达式或阈值描述',
    `yellow_description` varchar(500) DEFAULT NULL COMMENT '黄色预警描述',
    `orange_expression` varchar(500) DEFAULT NULL COMMENT '橙色预警表达式或阈值描述',
    `orange_description` varchar(500) DEFAULT NULL COMMENT '橙色预警描述',
    `red_expression`    varchar(500) DEFAULT NULL COMMENT '红色预警表达式或阈值描述',
    `red_description`   varchar(500) DEFAULT NULL COMMENT '红色预警描述',
    -- 抗抖动配置
    `persist_count`     int          DEFAULT '1' COMMENT '持续触发N个数据周期后才生成告警（防误报）',
    `silence_period`    int          DEFAULT '0' COMMENT '静默周期（数据采集周期数），期内重复触发仅累加次数',
    -- 状态
    `is_enabled`        tinyint      DEFAULT '1' COMMENT '是否启用: 0-禁用, 1-启用',
    `version`           int          DEFAULT '1' COMMENT '规则版本号（每次修改+1）',
    -- 标准列
    `create_by`         varchar(64)  DEFAULT NULL COMMENT '创建者',
    `create_time`       datetime     DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `update_by`         varchar(64)  DEFAULT NULL COMMENT '更新者',
    `update_time`       datetime     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    `del_flag`          tinyint      DEFAULT '0' COMMENT '删除标记: 0-正常, 1-删除',
    PRIMARY KEY (`id`),
    KEY `idx_criteria_type` (`monitor_type_id`),
    KEY `idx_criteria_content` (`monitor_content_id`),
    KEY `idx_criteria_hp` (`hazard_point_id`),
    KEY `idx_criteria_enabled` (`is_enabled`),
    KEY `idx_criteria_del` (`del_flag`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='告警判据表';
```

**与旧表关键差异：**

| 维度   | 旧表                          | 新表                                           |
|------|-----------------------------|----------------------------------------------|
| 设备绑定 | `device_id` + `device_name` | 移除（通过 sensor→device 间接关联）                    |
| 条件表达 | 每级一个 varchar 表达式            | `conditions_json` JSON 数组 + `logic_operator` |
| 指标精度 | `monitor_content_code` 字符串  | `monitor_content_id` FK 关联                   |
| 抗抖动  | 无                           | `persist_count` + `silence_period`           |
| 版本管理 | 无                           | `version` 字段 + `alarm_criteria_log` 表        |

**与旧表关键差异：**

| 维度   | 旧表                           | 新表                                         |
|------|------------------------------|--------------------------------------------|

#### 4.4.2 CriteriaEvaluator（判据条件评估器）

```java
@Component
public class CriteriaEvaluator {

    /**
     * 评估单条判据是否满足条件。
     *
     * @param criteria 判据（含 conditions_json）
     * @param currentValue 当前测量值
     * @param recentValues 最近 N 个值（用于复合判据如"小时变化 > 5"）
     * @return 触发的告警等级（蓝色=1 ~ 红色=4），0 = 未触发
     */
    public int evaluate(AlarmCriteria criteria, Double currentValue,
                        Map<String, List<Double>> recentValues) {
        List<CriteriaCondition> conditions = parseConditions(criteria.getConditionsJson());
        boolean matched;
        if ("AND".equals(criteria.getLogicOperator())) {
            matched = conditions.stream().allMatch(c -> evaluateCondition(c, currentValue, recentValues));
        } else {
            matched = conditions.stream().anyMatch(c -> evaluateCondition(c, currentValue, recentValues));
        }
        if (!matched) return 0;

        // 分级判定：从高到低依次检查
        if (evaluateLevelExpression(criteria.getRedExpression(), currentValue)) return 4;
        if (evaluateLevelExpression(criteria.getOrangeExpression(), currentValue)) return 3;
        if (evaluateLevelExpression(criteria.getYellowExpression(), currentValue)) return 2;
        if (evaluateLevelExpression(criteria.getBlueExpression(), currentValue)) return 1;
        return 0;
    }

    // 单个条件评估：支持 GT, GTE, LT, LTE, EQ, NEQ, BETWEEN, RATE_CHANGE 等操作符
    private boolean evaluateCondition(CriteriaCondition cond, Double val,
                                       Map<String, List<Double>> history) { ... }
}
```

**操作符支持清单：**

| 操作符           | 说明   | 示例                     |
|---------------|------|------------------------|
| `GT`          | 大于   | `value > 10`           |
| `GTE`         | 大于等于 | `value >= 10`          |
| `LT`          | 小于   | `value < 5`            |
| `LTE`         | 小于等于 | `value <= 5`           |
| `EQ`          | 等于   | `status == 1`          |
| `NEQ`         | 不等于  | `quality != 0`         |
| `BETWEEN`     | 区间   | `value BETWEEN 5,10`   |
| `RATE_CHANGE` | 变化速率 | `hour_change > 5 mm/h` |
| `ACCUMULATED` | 累计值  | `day_rain > 50`        |

## 六、技术决策记录

### 6.1 表达式引擎选择

| 方案         | 优点             | 缺点        | 结论          |
|------------|----------------|-----------|-------------|
| 手写 JSON 条件 | 可控、无需外部依赖、可序列化 | 仅支持预定义操作符 | **选用：基础判据** |
| Aviator    | 高性能、内置函数丰富     | 引入新依赖     | 不选用（v1 不需要） |
| Groovy     | 灵活、支持复杂脚本逻辑    | 需沙箱限制     | **选用：综合策略** |

### 6.2 告警持久次数存储

| 方案        | 优点         | 缺点        | 结论     |
|-----------|------------|-----------|--------|
| MySQL 临时行 | 持久化、不丢数据   | 高频写入压力大   | 不选用    |
| Redis 计数器 | 高性能、天然 TTL | 重启丢失（可接受） | **选用** |

使用 Redis key `alarm:pre-trigger:{criteriaId}:{hazardPointId}:{level}` 存储未达 persistCount 的预触发计数，TTL =
数据采集周期 × persistCount × 2。

### 6.3 判据缓存策略

- **本地缓存**：Caffeine Cache，TTL 60s，max 1000 条
- **失效通知**：Redis Pub/Sub，判据修改时广播失效消息
- 或简单方案：每次评估从 MySQL 查询（判据数量少，查询快），后续按需加缓存

### 6.4 Groovy 脚本安全

- GroovyShell 使用 `SecureASTCustomizer` 限制：
    - 禁止 `System.exit()`、`Runtime.exec()`、文件 IO、网络 IO
    - 允许导入白名单：`java.lang.Math`, `java.math.*`
    - 超时限制：执行超时 30s

### 6.5 旧表处理

由于告警模块无生产数据，采用**直接 DROP + 重建**策略（非灰度迁移）。DDL 脚本放置在 `db/upgrade/` 目录，按版本命名。
