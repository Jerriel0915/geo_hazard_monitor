## CRITICAL 问题

### C-1. COMPREHENSIVE 告警去重完全失效 — 每个数据点和每个 CRON 周期都创建重复告警

**文件：** `AlarmRecordServiceImpl.java:49-56`
**影响范围：** `AlarmEvaluationEngine.evaluateRealtimeStrategies()`, `ComprehensiveAlarmJob.executeStrategy()`

`createOrUpdateAlarm()` 的去重仅通过 `selectActiveByCriteria(criteriaId, hazardPointId)` 查找。COMPREHENSIVE 告警只设置
`strategyId` 不设置 `criteriaId`，导致 `if (record.getCriteriaId() != null)` 守卫跳过去重，每次调用都创建新记录。

**修复：** 新增 `selectActiveByStrategy` 查询 + 分支判断。

### C-2. `new BigDecimal(null)` NPE — malformed 传感器值导致评估管线崩溃

**文件：** `AlarmEvaluationEngine.java:202, 323`

`event.getValue()` 为 `Double`（可为 null），引擎未校验就直接 `new BigDecimal(event.getValue())`。一条 malformed
消息即可导致该条数据的整个评估中断。

**修复：** 在 `evaluate()` 入口添加 null guard。

## HIGH 问题

### H-1. GroovyScriptExecutor 每次调用创建新线程池 — 热路径资源泄漏

**文件：** `GroovyScriptExecutor.java:59`

`execute()` 内部每次创建 `Executors.newSingleThreadExecutor()`，REALTIME 策略每条数据触发一次，高频率下线程创建/销毁开销严重，超时后
`shutdownNow()` 无法保证线程终止。

**修复：** 改为共享 `ExecutorService` 实例字段，`@PreDestroy` 清理。

### H-2. `isInSilence()` 死代码 — ComprehensiveAlarmJob 静默检测永远返回 false

**文件：** `ComprehensiveAlarmJob.java:141-145`

方法注释说"由 AlarmDedupService 处理"，但 COMPREHENSIVE 路径从不调用 AlarmDedupService。CRON 策略每分钟无差别创建新告警。

**修复：** 实现 Redis 静默期检测或注入 AlarmDedupService 复用。

### H-3. `createOrUpdateAlarm` 忽略 `persistCount` / `silencePeriod` 参数

**文件：** `AlarmRecordServiceImpl.java:49`

方法签名声明了两个参数但完全不使用，误导调用方以为去重/静默在此处生效。

**修复：** 明确职责边界，补充文档说明去重是调用方职责。

### H-4. AlarmNotifier 绕过 IAlarmDispatchService 直接注入 Mapper

**文件：** `AlarmNotifier.java:34`

`IAlarmDispatchService` 接口已存在但缺少 `selectEnabledRules()` 方法，导致 AlarmNotifier 直接注入 Mapper，破坏分层架构。

**修复：** 为 IAlarmDispatchService 补充 `selectEnabledRules()` 方法。

### H-5. AlarmNotificationMapper.updateStatus SQL bug

**文件：** `AlarmNotificationMapper.xml:61-67`

`error_msg` 字段被赋值两次（if 块一次 + 无条件一次），静态文本中的逗号在 errorMsg 为 null 时造成 SQL 语法错误。

### H-6. 跨模块表 JOIN — 架构耦合

**文件：** `AlarmStrategyMapper.xml:111-118`

`selectHazardPointIdsByMonitorTypeId` 直接 JOIN `device_hazard_point` 和 `device_sensor` 表，绕过项目架构约定的跨模块
Service 接口。

### H-7. 3 个 selectById 方法缺少 `del_flag = 0` 过滤

**文件：** `AlarmCriteriaMapper.xml:79`, `AlarmStrategyMapper.xml:61`, `AlarmDispatchRuleMapper.xml:53`

列表查询有软删除过滤，但按 ID 查询没有。可通过 ID 绕过软删除访问已删除数据。

### H-8. 3 个 DTO 缺少验证注解

**文件：** `DispatchRuleCreateRequest.java`, `AlarmRecordDisposeRequest.java`, `BatchDisposeRequest.java`

无 `@NotBlank` / `@NotNull` / `@NotEmpty` 注解，malformed 请求直接穿透到持久层。
