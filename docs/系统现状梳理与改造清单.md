## 一、业务实体层级关系梳理

### 1.1 核心实体关系图

```
hazard_point_group (隐患点分组)
    │ 1:N (hazard_point.group_id → hazard_point_group.id)
    ▼
hazard_point (隐患点)
    │ N:M (via device_hazard_point)
    │     ├── fk_dhp_device → device.id
    │     └── fk_dhp_hp    → hazard_point.id
    ▼
device (设备)
    │ 1:N (device_sensor.device_id → device.id)
    ├── device_status_log (维修记录)
    ├── device_online_event_log (上下线记录)
    ├── video_device (视频设备，独立表)
    ▼
device_sensor (传感器) ── monitor_type_id → monitor_type (监测类型)
    │ 1:N (sensor_attribute.sensor_id → device_sensor.id)
    │     └── uk_sensor_attr_code (sensor_id, attr_code)
    │     └── monitor_content_id → monitor_content.id  [FK]
    ▼
sensor_attribute (传感器属性 / 测点)
    │
    │ FK 关联 + 快照副本
    ▼
monitor_content (监测内容定义) ── monitor_type_id → monitor_type
    │
monitor_type.category_id → monitor_category (监测大类, 平级 8 类)

时序数据路径 (IoTDB):
  root.geo_hazard.d{device_id}.s{sensor_no}.{attr_code}

业务数据 (MySQL):
  monitor_data (已废弃)
  alarm_criteria → alarm_record → alarm_notification
```

### 1.2 层级关系明细

| 层级  | 实体                                 | 主键 | 关键外键/关联                                                | 说明                               |
| ----- | ------------------------------------ | ---- | ------------------------------------------------------------ | ---------------------------------- |
| L1    | `hazard_point_group`                 | id   | —                                                           | 隐患点分组，如"崩塌监测组"         |
| L2    | `hazard_point`                       | id   | group_id → hazard_point_group.id                            | 具体隐患点，含经纬度、走向角       |
| L3    | `device`                             | id   | —                                                           | 采集设备，含 MQTT 认证账号         |
| L3'   | `video_device`                       | id   | —                                                           | 视频监控设备（独立体系）           |
| L4    | `device_hazard_point`                | id   | device_id + hazard_point_id (UNIQUE)                         | 设备与隐患点多对多绑定             |
| L4'   | `video_device_hazard_point`          | id   | video_device_id + hazard_point_id                            | 视频设备与隐患点绑定               |
| L5    | `device_sensor`                      | id   | device_id → device.id, monitor_type_id → monitor_type.id   | 设备下的传感器                     |
| L6    | `sensor_attribute`                   | id   | sensor_id → device_sensor.id, (sensor_id, attr_code) UNIQUE | 传感器具体测点属性                 |
| L7    | `monitor_type`                       | id   | —                                                           | 监测类型字典（雨量/位移/温湿度等） |
| L8    | `monitor_content`                    | id   | monitor_type_id → monitor_type.id                           | 监测内容指标定义                   |
| IoTDB | `root.geo_hazard.d{id}.s{no}.{attr}` | —   | device_id + sensor_no + attr_code                            | 时序数据存储                       |

### 1.3 关键字段映射链

```
MQTT 主题:
  sys/v1/{deviceCode}/{sensorNo}/updata
  gb/v1/{deviceCode}/{sensorNo}/updata

解析链路:
  deviceCode (主题) → device.code → device.id
  sensorNo   (主题) → device_sensor.sensor_no → device_sensor.id
  attr_code  (payload) → sensor_attribute.attr_code → IoTDB measurement

权限注解前缀:
  basic:*     — 基础数据管理（设备、传感器、监测类型、视频设备、隐患点分组）
  iot:*       — IoT 业务（隐患点管理）
  monitor:*   — 系统监控总览、MQTT 状态、日志
  system:*    — 用户、角色、菜单、组织
```

## 三、业务与逻辑问题清单

### 3.1 告警引擎完全缺失 【严重程度：CRITICAL】

**现状：**

- 数据库表 `alarm_criteria`、`alarm_dispatch_rule`、`alarm_notification`、`alarm_record` 已完整定义
- API 接口文档（第5章）已设计完整的告警判据 CRUD、分发规则管理、告警记录查询接口
- 但 zwei-iot 模块中搜索 `alarm` 关键词结果为 **零 Java 文件**
- 开发方案文档明确标注"本期不落地，待后续迭代"

**业务影响：**

- 系统的核心价值——地质灾害预警——完全不可用
- 设备采集的数据只能用于事后查看，无法实时预警
- 告警判据虽然能通过 API 配置，但配置后没有任何引擎执行

**改造建议：**

- P0 优先级，建立告警引擎微服务或模块
- 在 MonitorIngestConsumerService 写入 IoTDB 后发布数据变更事件
- 告警引擎监听事件，匹配判据表达式，生成 alarm_record
- 分发引擎根据 alarm_dispatch_rule 生成 alarm_notification

### 3.6 监测类型 device_type 字段语义歧义 【严重程度：MEDIUM】

**现状：**

- `monitor_type` 表名为"监测类型"，是描述**监测什么**的字典表（雨量/位移/温湿度等）
- 但其 `device_type` 字段取值为"1=直连设备, 2=传感器, 3=RTU"，这是描述**设备形态**的分类
- 新增传感器时要求"仅允许选择 deviceType=2 的监测类型"

**问题：**

- 监测类型（如"雨量监测"）和"这个监测用什么设备形态做"是两个正交概念
- 把设备形态分类放在监测类型表里，导致创建监测类型时必须关心设备形态
- 如果"雨量监测"既可以用直连雨量计(device_type=1)也可以用传感器(device_type=2)，则只能建两条记录

**改造建议：**

- 将 `device_type` 从 `monitor_type` 移至 `device` 表或 `device_sensor` 表
- 或拆分为两个独立维度：监测类型的物理属性 vs 设备部署形态

### 3.7 权限标识命名空间不统一 【严重程度：MEDIUM】

**现状：**

| 域        | 权限前缀                             |
|----------|----------------------------------|
| 隐患点 CRUD | `iot:hazard-point:*`             |
| 隐患点分组    | `basic:hazardPointGroup:*`       |
| 设备管理     | `basic:device:*`                 |
| 设备账号     | `basic:device:auth:*`            |
| 传感器      | `basic:sensor:*`                 |
| 监测类型     | `basic:monitorType:*`            |
| 监测内容     | `basic:monitorContent:*`         |
| 视频设备     | `basic:videoDevice:*`            |
| 监测数据查询   | `basic:device:query` (复用设备的查询权限) |
| 系统监控     | `monitor:*`                      |
| 用户角色菜单   | `system:*`                       |

**问题：**

- 同一业务域（IoT 设备管理）出现两种权限前缀 `iot:` 和 `basic:`
- `basic:sensor:*` 与 `basic:device:auth:*` 的资源层级不一致
- 监测数据查询接口复用 `basic:device:query`，语义不准确
- 分组管理用 `basic:hazardPointGroup` 但隐患点管理用 `iot:hazard-point`，同一实体域不同前缀

**改造建议：**

- 统一为 `iot:{resource}:{action}` 或 `basic:{resource}:{action}` 其中一种
- 建议采用：`iot:hazard-point:*`, `iot:device:*`, `iot:sensor:*`, `iot:monitor-type:*`, `iot:video-device:*`
- 监测数据应有独立权限：`iot:monitor-data:query`

### 3.8 视频设备集成程度浅 【严重程度：MEDIUM】

**现状：**

- 仅有 video_device 基本 CRUD
- 可绑定到隐患点
- 无流媒体转发/代理功能

### 3.9 device_sensor 表 sensor_code 与 sensor_no 双字段冗余 【已修复 ✅】

**原因分析：**

经过全代码库排查（SQL/Java/XML/TS/Vue/docs），两个字段**语义不同、使用场景独立**，不是冗余而是正交维度：

| 维度       | sensor_code                                       | sensor_no                     |
|----------|---------------------------------------------------|-------------------------------|
| **语义**   | 全局业务标识                                            | 设备内 MQTT 路由键                  |
| **唯一性**  | 全局唯一 (`uk_device_sensor_code`)                    | 设备内唯一 (`uk_device_sensor_no`) |
| **依赖方**  | API CRUD、告警脚本（Blockly）                            | MQTT 发布/订阅、IoTDB 路径、时序数据查询    |
| **长度**   | varchar(100)                                      | varchar(32)                   |
| **生成规则** | `deviceCode + "_" + sensorNo`（设备注册）/ 用户手填（Web 后台） | 用户指定 / 默认等于 sensorCode        |
| **可变性**  | 创建后不可修改                                           | 创建后可修改                        |

**已实施的修复（2026-06-08）：**

| 项目                             | 处理方式       | 说明                                                                                                           |
|--------------------------------|------------|--------------------------------------------------------------------------------------------------------------|
| DB 注释                          | 修正         | `sensor_code` → "传感器全局编码（全局唯一，API CRUD 主标识）"；`sensor_no` → "传感器主题编号（设备内唯一，MQTT 主题路由 / IoTDB 路径键）"            |
| API 文档                         | 修正         | 同上述语义更新 + 新增`sensorNo` 唯一性约束说明                                                                               |
| `MqttServerSubscribeValidator` | **BUG 修复** | topic 第二段实际为 sensor_no，原代码错误地将其赋值给 sensorCode 并查询 sensor_code 列；当两字段值不同时订阅校验会失败。改为使用 sensorNo 查询 sensor_no 列 |
| 保留双字段                          | 确认         | 两个字段服务不同层级，合并会导致 IoTDB 路径污染 + 软删除 #DEL# 重写扩散 + MQTT 主题变长                                                     |

**配套改造：**

### 3.14 sensor_attribute → monitor_content 关联约束 【已修复 ✅】

**原问题：** 创建 sensor_attribute 时，`attr_code` 可与 monitor_content 完全无关，invalid monitor_content_id 被静默吞错。

**实际状态（经代码排查）：**

- `sensor_attribute.monitor_content_id` 列 **已存在**（V2.0_01 DDL 新增，`bigint DEFAULT NULL`）
- 普通索引 `idx_sensor_attr_content` **已存在**
- Java 域模型 / API DTO / MyBatis 映射 **已全面支持**
- 数据回填 **已完成**（V2.0_02 通过 `attr_code = monitor_content.code` JOIN）
- 自动回填 unit **已实现**（`populateFromContent()`）

**已实施的修复（2026-06-08）：**

| 项目                      | 处理方式         | 说明                                                                   |
|-------------------------|--------------|----------------------------------------------------------------------|
| `populateFromContent()` | 静默吞错 → 显式抛异常 | `mc == null` 时抛出 `ServiceException("监测内容不存在或已停用")`，等效 FK RESTRICT 语义 |
| `attrCode` 自动回填         | 新增           | 传`monitorContentId` 且未传 `attrCode` 时，自动取 `monitor_content.code`      |

**为何不引入数据库外键约束：**

| 风险             | 说明                                                                                   |
|----------------|--------------------------------------------------------------------------------------|
| 软删除冲突          | 系统全量使用`del_flag` 逻辑删除，MySQL FK 不理解软删除——物理行存在即满足约束，但应用层按 `del_flag=0` 过滤后查不到，造成"僵尸引用" |
| 物理清理阻塞         | 若未来需物理清理已软删除的`monitor_content`，FK 会阻止 DELETE                                         |
| ON DELETE 语义困境 | `CASCADE` 误删传感器属性；`SET NULL` 静默丢数据；`RESTRICT` 阻塞运维                                   |
| 项目一致性          | 本系统所有跨表关联（device→sensor, sensor→attribute）均使用应用层校验 + 索引，无一处使用 FK                     |

**配套改造：**

- `DeviceSensorServiceImpl.populateFromContent()`: 无效/已停用 `monitorContentId` → 抛异常；自动回填 `attrCode` 和 `unit`

### 3.15 隐患点 device_count 维护方式落后 【已修复 ✅】

**原现状：**

```sql
-- 每次 bind/unbind 都执行子查询全量重算
UPDATE hazard_point SET device_count = (
    SELECT COUNT(*) FROM device_hazard_point WHERE hazard_point_id = #{id}
) WHERE id = #{id};
```

**已实施的修复（2026-06-08）：**

| 场景     | 原方式       | 新方式                                                | 说明                                                                     |
| -------- | ------------ | ----------------------------------------------------- | ------------------------------------------------------------------------ |
| 解绑设备 | COUNT 子查询 | `UPDATE device_count = GREATEST(device_count - N, 0)` | 用实际删除行数原子递减，无竞态                                           |
| 绑定设备 | COUNT 子查询 | 保持不变                                              | REPEATABLE READ 下并发 bind 无法通过快照读准确计算 delta，保留子查询方案 |
| 删除设备 | COUNT 子查询 | 保持不变                                              | 低频操作，正确性优先                                                     |

> **为什么不改为原子递增**：经代码审查发现，MySQL REPEATABLE READ 隔离级别下，`bindDevices` 若先快照读已有绑定再原子递增，两个并发
> bind 事务会基于同一快照计算 delta，导致 `device_count` 漂移（超过实际值）。正确方案需要 `SELECT ... FOR UPDATE` 悲观锁或改为
> READ COMMITTED，权衡后保持子查询 COUNT 作为更安全的折中。

**配套改造：**

- `HazardPointMapper`: 新增 `incrementDeviceCount(id, delta)` + `decrementDeviceCount(id, delta)` 原子 SQL
- `DeviceHazardPointMapper`: 新增 `selectDeviceIdsByHazardPointId(hazardPointId)` — 保留供其他场景使用
- `DeviceHazardPointServiceImpl.unbindDevices()`: 原子减量替代子查询刷新
- `DeviceHazardPointServiceImpl.bindDevices()`: 保持 `refreshDeviceCountById`（并发安全考虑）
- `DeviceServiceImpl.deleteDevice()`: 保持 `refreshDeviceCountById` 不变（低频路径）

## 五、架构优化建议（非功能需求）

### 5.1 模块边界优化

当前 zwei-iot 模块承担了过多职责：设备、传感器、隐患点、监测类型、时序数据、MQTT broker、视频设备。建议拆分为：

- **zwei-iot-device** — 设备全生命周期 + 传感器 + 认证账号
- **zwei-iot-hazard** — 隐患点 + 分组 + 绑定关系
- **zwei-iot-ingest** — MQTT 接入 + 数据解析 + IoTDB 写入
- **zwei-iot-alarm** — 告警引擎 + 判据执行 + 通知分发
- **zwei-iot-video** — 视频设备管理（独立演进）

### 5.2 事件驱动解耦

当前 MQTT 消息解析链路虽然是异步的（Redis Stream），但告警通知等下游场景仍缺乏事件总线。建议：

- 在 IoTDB 写入成功后发布 `MonitorDataIngestedEvent`（含 deviceId, sensorId, attrCode, value, dataTime）
- 告警引擎监听 `MonitorDataIngestedEvent` 进行判据匹配
- 通知服务监听 `AlarmTriggeredEvent` 进行多通道分发

### 5.3 监测类型与监测内容的模型重构

当前模型使得监测类型、监测内容、传感器属性三者通过编码字符串耦合。建议：

```
monitor_type (监测类型: 雨量、位移...)
  └── monitor_content (监测内容定义: 小时雨量、日雨量...)
        └── sensor_attribute (传感器属性, FK→monitor_content.id)
              └── attr_code = monitor_content.code (参照完整性)
```
