## 一、业务实体层级关系梳理

### 1.1 核心实体关系图

```
hazard_point_group (隐患点分组)
    │ 1:N (hazard_point.group_id → hazard_point_group.id)
    ▼
hazard_point (隐患点)
    │ N:M (via device_hazard_point)
    │     ├── fk_dhp_device → device.id
    │     └── fk_dhp_hp    → hazard_point.id
    ▼
device (设备)
    │ 1:N (device_sensor.device_id → device.id)
    ├── video_device (视频设备，独立表，通过 video_device_hazard_point 关联隐患点)
    ▼
device_sensor (传感器) ── monitor_type_id → monitor_type (监测类型)
    │ 1:N (sensor_attribute.sensor_id → device_sensor.id)
    │     └── uk_sensor_attr_code (sensor_id, attr_code)
    ▼
sensor_attribute (传感器属性 / 测点)
    │
    │ 逻辑映射 (编码同名约定)
    ▼
monitor_content (监测内容定义) ── monitor_type_id → monitor_type

时序数据路径 (IoTDB):
  root.geo_hazard.d{device_id}.s{sensor_no}.{attr_code}

业务数据 (MySQL):
  monitor_data (已废弃，不再承接新数据)
  alarm_criteria → alarm_record → alarm_notification
```

### 1.2 层级关系明细

| 层级 | 实体 | 主键 | 关键外键/关联 | 说明 |
|------|------|------|--------------|------|
| L1 | `hazard_point_group` | id | — | 隐患点分组，如"崩塌监测组" |
| L2 | `hazard_point` | id | group_id → hazard_point_group.id | 具体隐患点，含经纬度、走向角 |
| L3 | `device` | id | — | 采集设备，含 MQTT 认证账号 |
| L3' | `video_device` | id | — | 视频监控设备（独立体系） |
| L4 | `device_hazard_point` | id | device_id + hazard_point_id (UNIQUE) | 设备与隐患点多对多绑定 |
| L4' | `video_device_hazard_point` | id | video_device_id + hazard_point_id | 视频设备与隐患点绑定 |
| L5 | `device_sensor` | id | device_id → device.id, monitor_type_id → monitor_type.id | 设备下的传感器 |
| L6 | `sensor_attribute` | id | sensor_id → device_sensor.id, (sensor_id, attr_code) UNIQUE | 传感器具体测点属性 |
| L7 | `monitor_type` | id | — | 监测类型字典（雨量/位移/温湿度等） |
| L8 | `monitor_content` | id | monitor_type_id → monitor_type.id | 监测内容指标定义 |
| IoTDB | `root.geo_hazard.d{id}.s{no}.{attr}` | — | device_id + sensor_no + attr_code | 时序数据存储 |

### 1.3 关键字段映射链

```
MQTT 主题:
  sys/v1/{deviceCode}/{sensorNo}/updata
  gb/v1/{deviceCode}/{sensorNo}/updata

解析链路:
  deviceCode (主题) → device.code → device.id
  sensorNo   (主题) → device_sensor.sensor_no → device_sensor.id
  attr_code  (payload) → sensor_attribute.attr_code → IoTDB measurement

权限注解前缀:
  basic:*     — 基础数据管理（设备、传感器、监测类型、视频设备、隐患点分组）
  iot:*       — IoT 业务（隐患点管理）
  monitor:*   — 系统监控总览、MQTT 状态、日志
  system:*    — 用户、角色、菜单、组织
```

## 三、业务与逻辑问题清单

### 3.1 告警引擎完全缺失 【严重程度：CRITICAL】

**现状：**
- 数据库表 `alarm_criteria`、`alarm_dispatch_rule`、`alarm_notification`、`alarm_record` 已完整定义
- API 接口文档（第5章）已设计完整的告警判据 CRUD、分发规则管理、告警记录查询接口
- 但 zwei-iot 模块中搜索 `alarm` 关键词结果为 **零 Java 文件**
- 开发方案文档明确标注"本期不落地，待后续迭代"

**业务影响：**
- 系统的核心价值——地质灾害预警——完全不可用
- 设备采集的数据只能用于事后查看，无法实时预警
- 告警判据虽然能通过 API 配置，但配置后没有任何引擎执行

**改造建议：**
- P0 优先级，建立告警引擎微服务或模块
- 在 MonitorIngestConsumerService 写入 IoTDB 后发布数据变更事件
- 告警引擎监听事件，匹配判据表达式，生成 alarm_record
- 分发引擎根据 alarm_dispatch_rule 生成 alarm_notification

---

### 3.2 设备状态管理多维度重叠 【严重程度：HIGH】

**现状：**
`device` 表存在三个状态相关的字段：

| 字段 | 含义 | 取值 |
|------|------|------|
| `device.status` | 业务状态 | 1=正常, 2=故障, 3=离线 |
| `device.run_status` | 运行状态 | 0=未知, 1=运行中, 2=停止 |
| `device_online_status.status` | 在线状态 | 0=离线, 1=在线 |

**问题分析：**
- `device.status=3(离线)` 与 `device_online_status.status=0(离线)` 语义重叠
- `device.run_status=1(运行中)` 与 `device_online_status.status=1(在线)` 概念相近但不完全等价
- 三个字段的同步逻辑不清晰——MQTT 断连更新 `device_online_status` 但 `device.status` 和 `device.run_status` 是否同步更新？
- run_status 描述"运行中/停止"但缺乏明确的含义（停止是指设备关机？还是指令停报？）
- 测试数据中 device.id=1 的 status=1(正常) 但 run_status=2(停止)，说明逻辑不一致

**改造建议：**
- 统一设备状态模型，建议：
  - `device.status` → 保留为业务管理状态（正常/故障/停用），由人工操作变更
  - `device_online_status.status` → 保留为实时在线状态，由 MQTT 事件驱动
  - `device.run_status` → 评估是否可废弃，其语义已被前两者覆盖
- 明确状态转换规则和同步策略

### 3.3 sensor_attribute 更新策略有数据丢失风险 【严重程度：HIGH】

**现状：**
- `PUT /api/v1/sensors/{id}` 修改传感器时，对 `attrList` 的处理逻辑为：
  1. 已有 `id` 的属性 → 更新
  2. 无 `id` 的属性 → 新增
  3. **未出现在请求中的原有属性 → 删除**
- 这是一个变相的"先删后插"模式

**风险：**
- 前端并发提交或请求丢失字段时，属性会被非预期删除
- 属性删除后，关联的 IoTDB 时序数据虽然不丢失，但属性元数据（初始值、阈值范围）丢失
- 告警判据引用的 `monitor_content_code` 与实际 sensor_attribute 的 `attr_code` 出现断链

**改造建议：**
- 增加显式的属性删除标记字段，而非用"不存在"隐式表达
- 或改为增量更新模式：明确区分新增/更新/删除操作

### 3.5 密码重置的 forceOffline 参数不生效 【严重程度：MEDIUM】

**现状：**
```java
// DeviceServiceImpl.java
saveAuthAuditLog(..., buildResetPasswordDetail(resetReason, forceOffline));
```
- `forceOffline` 仅在审计日志中记录 `|forceOffline=true`
- 未实际调用任何 MQTT 断连逻辑（如 kick client、revoke session）

**业务影响：**
- 密码重置后，旧密码的 MQTT 连接仍然有效
- 直到旧客户端心跳超时或主动重连为止，存在安全窗口

**改造建议：**
- `forceOffline=true` 时调用 MqttHttpApiClient 的 kick 接口强制断开设备 MQTT 连接
- 或通过 MqttDeviceSessionRegistry 发布内部断连指令

### 3.6 监测类型 device_type 字段语义歧义 【严重程度：MEDIUM】

**现状：**
- `monitor_type` 表名为"监测类型"，是描述**监测什么**的字典表（雨量/位移/温湿度等）
- 但其 `device_type` 字段取值为"1=直连设备, 2=传感器, 3=RTU"，这是描述**设备形态**的分类
- 新增传感器时要求"仅允许选择 deviceType=2 的监测类型"

**问题：**
- 监测类型（如"雨量监测"）和"这个监测用什么设备形态做"是两个正交概念
- 把设备形态分类放在监测类型表里，导致创建监测类型时必须关心设备形态
- 如果"雨量监测"既可以用直连雨量计(device_type=1)也可以用传感器(device_type=2)，则只能建两条记录

**改造建议：**
- 将 `device_type` 从 `monitor_type` 移至 `device` 表或 `device_sensor` 表
- 或拆分为两个独立维度：监测类型的物理属性 vs 设备部署形态

### 3.7 权限标识命名空间不统一 【严重程度：MEDIUM】

**现状：**

| 域 | 权限前缀 |
|------|------|
| 隐患点 CRUD | `iot:hazard-point:*` |
| 隐患点分组 | `basic:hazardPointGroup:*` |
| 设备管理 | `basic:device:*` |
| 设备账号 | `basic:device:auth:*` |
| 传感器 | `basic:sensor:*` |
| 监测类型 | `basic:monitorType:*` |
| 监测内容 | `basic:monitorContent:*` |
| 视频设备 | `basic:videoDevice:*` |
| 监测数据查询 | `basic:device:query` (复用设备的查询权限) |
| 系统监控 | `monitor:*` |
| 用户角色菜单 | `system:*` |

**问题：**
- 同一业务域（IoT 设备管理）出现两种权限前缀 `iot:` 和 `basic:`
- `basic:sensor:*` 与 `basic:device:auth:*` 的资源层级不一致
- 监测数据查询接口复用 `basic:device:query`，语义不准确
- 分组管理用 `basic:hazardPointGroup` 但隐患点管理用 `iot:hazard-point`，同一实体域不同前缀

**改造建议：**
- 统一为 `iot:{resource}:{action}` 或 `basic:{resource}:{action}` 其中一种
- 建议采用：`iot:hazard-point:*`, `iot:device:*`, `iot:sensor:*`, `iot:monitor-type:*`, `iot:video-device:*`
- 监测数据应有独立权限：`iot:monitor-data:query`

### 3.8 视频设备集成程度浅 【严重程度：MEDIUM】

**现状：**
- 仅有 video_device 基本 CRUD
- 可绑定到隐患点
- 无流媒体转发/代理功能
- 无 WebRTC/RTSP 网关集成

**业务影响：**
- 前端虽然能展示视频设备列表和绑定关系，但无法实际播放视频流
- 视频监控是地灾监测的重要可视化手段

**改造建议：**
- 集成流媒体服务（如 ZLMediaKit、Janus、MediaMTX）
- 或前端直接通过 RTSP→WebRTC 网关播放（如通过 flv.js / WebRTC）

### 3.9 device_sensor 表 sensor_code 与 sensor_no 双字段冗余 【严重程度：LOW】

**现状：**
```sql
`sensor_code` varchar(100) NOT NULL COMMENT '传感器编号',  -- 全局唯一
`sensor_no`   varchar(32)  NOT NULL COMMENT '传感器编号',  -- 设备内唯一 (device_id, sensor_no)
```

**问题：**
- 两个字段中文注释都是"传感器编号"
- `sensor_code` 全局唯一，用于 API CRUD
- `sensor_no` 设备内唯一，用于 MQTT 主题路由
- 实际测试数据中 `sensor_code = sensor_no = 'test_sensor_001'`
- 两个字段功能重叠，增加了理解成本

**改造建议：**
- 保留 `sensor_code` 为全局唯一业务标识
- 保留 `sensor_no` 为 MQTT 主题中的短编号
- 明确两者使用场景差异，更新注释为"传感器全局编码"和"传感器主题编号"
- 若业务上始终相等，可考虑合并

### 3.11 缺少设备运行参数模型 【严重程度：MEDIUM】

**现状：**
- 设备表无以下运行参数字段：
  - 采样间隔 (sampling_interval)
  - 上传间隔 (upload_interval)
  - 加报间隔 (boost_interval)
  - 心跳间隔 (heartbeat_interval)
- 这些参数对设备管理和告警判断至关重要

**改造建议：**
- 在 `device` 表或新增 `device_config` 表中补充运行参数
- 支持通过 MQTT 指令下发方式（待实现）推送参数到设备

---

### 3.12 IoTDB 缺少数据生命周期管理 【严重程度：MEDIUM】

**现状：**
- 无 TTL (Time-To-Live) 配置
- 无冷热数据分层策略
- 无自动归档/压缩策略

**风险：**
- 随着设备接入量增加，IoTDB 存储无限增长
- 历史数据查询性能逐步下降

**改造建议：**
- 配置 IoTDB TTL（如原始数据保留 12 个月）
- 实现自动降采样聚合（如 72h 以上数据聚合为小时级）
- 定期评估是否需要冷数据迁移

---

### 3.13 缺少告警通知渠道实现 【严重程度：HIGH】

**现状：**
- `alarm_dispatch_rule` 表定义了 channel 字段（SYSTEM/SMS/EMAIL）
- `alarm_notification` 表已定义通知记录结构
- 但无任何实际的通知发送实现

**业务影响：**
- 即便告警引擎实现后，告警消息也只能落库，无法推送到责任人

**改造建议：**
- 实现多通道通知服务：
  - SYSTEM — 复用已有 SSE 通知推送机制（sys_notice）
  - SMS — 集成短信服务商 API
  - EMAIL — 集成邮件服务

---

### 3.14 device_sensor 缺少与 monitor_content 的显式关联 【严重程度：MEDIUM】

**现状：**
- `device_sensor` 通过 `monitor_type_id` 关联到监测类型
- `sensor_attribute.attr_code` 与 `monitor_content.code` 通过编码约定关联
- 但数据库层面无外键约束

**问题：**
- 创建 sensor_attribute 时，attr_code 可以与 monitor_content 完全无关
- 告警判据表达式引用的 `monitor_content_code` 可能找不到对应的 sensor_attribute
- 数据查询时需要通过 `attr_code` 字符串匹配，而非 JOIN

**改造建议：**
- sensor_attribute 增加 `monitor_content_id` 外键
- 或建立 sensor_attribute.attr_code → monitor_content.code 的参照完整性约束

---

### 3.15 隐患点 device_count 维护方式落后 【严重程度：LOW】

**现状：**
```sql
-- HazardPointMapper.xml
UPDATE hazard_point SET device_count = (
    SELECT COUNT(*) FROM device_hazard_point WHERE hazard_point_id = #{id}
) WHERE id = #{id};
```
- 通过子查询批量更新，而非在绑定/解绑时实时加减

**改造建议：**
- 在 `DeviceHazardPointServiceImpl.bindDevices()` 和 `unbindDevices()` 中直接 +1/-1
- 或完全取消持久化字段，改为查询时 JOIN COUNT

---

### 3.16 缺少设备注册码管理 【严重程度：MEDIUM】

**现状：**
- 设备注册接口 `POST /api/v1/device-registry/register` 需要 `registerCode`
- 但系统中无注册码生成/管理/分发功能
- 数据库无注册码表

**问题：**
- 实际上线部署时，厂商凭什么注册？注册码如何发放和回收？

**改造建议：**
- 新增 `device_register_code` 表
- 支持后台生成批量注册码、设置有效期/使用次数限制
- 支持二维码导出

## 五、架构优化建议（非功能需求）

### 5.1 模块边界优化

当前 zwei-iot 模块承担了过多职责：设备、传感器、隐患点、监测类型、时序数据、MQTT broker、视频设备。建议拆分为：

- **zwei-iot-device** — 设备全生命周期 + 传感器 + 认证账号
- **zwei-iot-hazard** — 隐患点 + 分组 + 绑定关系
- **zwei-iot-ingest** — MQTT 接入 + 数据解析 + IoTDB 写入
- **zwei-iot-alarm** — 告警引擎 + 判据执行 + 通知分发
- **zwei-iot-video** — 视频设备管理（独立演进）

### 5.2 事件驱动解耦

当前 MQTT 消息解析链路虽然是异步的（Redis Stream），但告警通知等下游场景仍缺乏事件总线。建议：

- 在 IoTDB 写入成功后发布 `MonitorDataIngestedEvent`（含 deviceId, sensorId, attrCode, value, dataTime）
- 告警引擎监听 `MonitorDataIngestedEvent` 进行判据匹配
- 通知服务监听 `AlarmTriggeredEvent` 进行多通道分发

### 5.3 监测类型与监测内容的模型重构

当前模型使得监测类型、监测内容、传感器属性三者通过编码字符串耦合。建议：

```
monitor_type (监测类型: 雨量、位移...)
  └── monitor_content (监测内容定义: 小时雨量、日雨量...)
        └── sensor_attribute (传感器属性, FK→monitor_content.id)
              └── attr_code = monitor_content.code (参照完整性)
```

## 六、总结

系统在设备接入闭环方面（注册→认证→上报→解析→落库→查询）已基本闭环，核心数据通路可运行。但在业务价值闭环方面（采集→告警→通知→处置）存在严重缺口——**告警引擎**和**通知分发**完全缺失。

此外，**国标协议解析**、**设备状态模型**、**权限命名**等方面存在技术债务，建议按优先级分阶段治理。

**当前分支 (web260429) 应完成的核心目标：**
1. 告警引擎基础框架 + 判据执行
2. 国标协议解析器正式实现
3. 设备状态模型统一
